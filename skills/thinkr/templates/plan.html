API Rate Limits

Every public API key gets a token bucket in Redis. The gateway takes a token per request and answers 429 when the bucket is empty, so one noisy client can no longer slow the API for everyone else.

How a request is checked

The check lives in the gateway, before any service code runs. It costs one Redis round trip per request.

A request arrives with its API key. The gateway takes one token from that key's bucket. One Redis call, about 1 ms. Tokens left: forward the request and tell the client how many remain. Bucket empty: answer 429 at once. The Orders API never sees the request.

Which algorithm should count requests?

Token bucketAllows short bursts up to the bucket size, then a steady rate. One atomic Redis script per request. Sliding window logExact counts over the last 60 s, no bursts. Stores one entry per request, so memory grows with traffic. Fixed windowSimplest: one counter per minute. Lets a client send double the limit across a minute boundary.

What should each limit be counted against?

API keyThe default. Each integration gets its own budget. OrganizationCaps a customer with many keys. Needs an org lookup per request, cached in the gateway. IP addressCatches unauthenticated abuse. Punishes customers behind a shared NAT. EndpointLets expensive routes such as exports have their own, lower limit.

When Redis does not answer within 20 ms, what should the gateway do?

Let the request throughThe API stays up; limits stop working until Redis is back. An alert fires. Reject with 503Limits always hold, and a Redis outage becomes an API outage. Count in gateway memoryRough limits per gateway instance. More code to write and test.

Rollout

Limits start in shadow mode: the gateway logs what it would have rejected, so we can set the numbers from real traffic before anyone sees a 429.
